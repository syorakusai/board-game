# Board（貴族のひそめごと）

「貴族のひそめごと」は、イラストカードをもとに、親が作ったワードを子が見抜く、会話型の対人カードゲームです。

副題：見抜くか、欺くか。社交場の言葉遊び

## コンセプト

カードには、ひとつのボケとして成立する奇妙な情景が描かれています。

親はカードを見て、そのボケに対する新しいワードを1つ作ります。システムはカードに登録済みの公式ワードから3個を選び、親ワードと合わせた4個をシャッフルして公開します。

子は会話や親への質問を通じて、4つの候補から親ワードを推理します。

## 用語

- 親：カードを引き、親ワードを作成するプレイヤー
- 子：親が作成した親ワードを当てるプレイヤー
- カード：イラストと公式ワードが登録されたカード
- 公式ワード：カードにあらかじめ登録されたワード
- 親ワード：親がカードのイラストを見て新たに作成するワード

## ゲームルール

### 1ラウンドの流れ

1. 伏せ札の山からカードを1枚引きます。
2. 既に知っているカードだった場合は、カードを山札へ戻さずに「別の札を引く」を選び、ひとつ手前のCARD DRAW画面から別の札を引きます。
2. カードのイラストを全員に公開します。
3. カードに登録された公式ワードから、システムがランダムに3個を選びます。
4. 親にスマートフォンを渡します。
5. 親の本人確認後、親はカード画像と公式ワード3個を確認します。
6. 親はイラストに対する親ワードを1つ入力し、「ひそめる」を押します。
7. 公式ワード3個と親ワード1個、合計4個を自動でシャッフルします。
8. 条件画面で推理時間を1分・2分・3分・5分から選びます。初期値は2〜4人では2分、5〜6人では3分です。
9. 「推理を開始」を押すと、言葉のお披露目から宴の推理へ移り、設定した推理時間のカウントダウンが始まります。
10. 設定した推理時間のあいだ、全員で会話しながら推理します。
11. 時間終了後、各子は親ワードだと思う候補を1つ選びます。
12. 全員の回答後、「ひそめごと開帳」を押します。
13. 親ワード、正解者、不正解者、得点結果を表示します。
14. 親を交代して次の席へ進みます。

### 推理中のルール

- 子は親に質問できます。
- 親は質問に答えられます。
- 親は親ワードを直接明かしてはいけません。
- 各ラウンド画面の右上には「戦績」と「≡」メニューがあります。「≡」メニューから遊び方の確認と、ゲームの退出ができます。
- ゲーム中に遊び方を開いても、進行状態は保持されます。推理中は遊び方・戦績・カード拡大・「≡」メニューの表示中もカウントダウンを継続し、時間切れになった瞬間にそれらを閉じて「お時間です」の画面へ遷移します。
- ひそめごと開帳まで、親ワードと正誤判定は表示しません。

### 得点

| 結果 | 正解した子 | 親 |\n|---|---:|---:|\n| 一部の子だけ正解 | 正解者に＋1 | 0 |\n| 全員正解 | 全員に＋1 | −1 |\n| 全員不正解 | 0 | ＋1 |\n\n得点の下限は0ポイントとし、0ポイント未満にはなりません。\n\n2人対戦では子が1人になるため、親に対する「全員正解時の−1ポイント」「全員不正解時の＋1ポイント」は適用しません。\n\n| 2人対戦の結果 | 子 | 親 |\n|---|---:|---:|\n| 子が正解 | ＋1 | 0 |\n| 子が不正解 | 0 | 0 |

画面上の結果表示は以下に統一します。

- 全員不正解：`全員不正解。親プラス1ポイント`
- 全員正解：`全員正解。子プラス1ポイント、親マイナス1ポイント`
- 一部の子が正解：`正解した子に1ポイント`

### 勝利条件

先に5ポイントへ到達したプレイヤーを勝利者とします。

同じラウンドで複数人が5ポイント以上に到達した場合は、到達した全員を同率の勝利者として扱います。勝者どうしの優劣付けやタイブレークは行いません。

### プレイヤー登録と親順

- プレイヤー人数は2〜6人です。
- 人数分のプレイヤー名を入力します。
- 空欄の名前と、同じ名前の重複登録はできません。
- 登録した名前は同じ端末のブラウザに保存し、再読み込み後も復元します。
- 保存した名前は対戦人数にかかわらず、一人目・二人目など同じ番号の入力欄へ復元します。人数を増やした場合は、保存されていない追加欄だけ空欄になります。
- 保存されていない入力欄は、初期値として「客人1」〜「客人6」を表示します。
- 最初の親はランダムに決定します。
- 以後は決定した順番で親を交代します。
- 各操作前に、現在スマートフォンを操作するプレイヤーの本人確認を行います。

## カード制作方針

- カード画像は、縦1536ピクセル、横1024ピクセルで制作します。
- カードはトランプのような縦長の比率にします。
- 豪華な装飾枠を設けます。
- 画像キャンバス全体を、一枚の完成したカード面として構成します。
- カードが白い背景や余白の中に浮かんでいるような構図にはしません。
- 外側の装飾枠の外側に、白色・無地・未描画の余白を作りません。
- 背景、装飾枠、情景を含むカード全体で、1536×1024ピクセルの画面を隙間なく使用します。
- 一枚のカードを画面内に配置したような表現ではなく、画面全体が最初から一枚のカードとして成立するように描きます。
- 中央には、ひとつのボケとして成立する奇妙な情景を描きます。
- イラストは、少し毒気のある風刺画・カーニバルポスター風のタッチで統一します。
- カード内に文字やロゴは入れません。
- 題材や発想の型を偏らせません。
- 合体的な絵だけに偏らず、競技、職業、行事、日常の誇張、動物、建物、道具、風景、失敗や勘違いなどを混ぜます。
- カードを見た時点で、プレイヤーがツッコミや解釈を考えたくなる情景を目指します。
- 画面全体の明度や色調は、題材や情景に合わせて変化させます。
- 作品ごとに明るい配色・暗い配色のどちらも許容し、毎回同じ方向へ寄せません。
- ただし、暗い配色の場合も、主役や情景の細部が見分けられるようにします。

## 公式ワード制作方針

公式ワードは、カードのイラストを確認したうえで、その情景に対する反応として作成します。

ワードセット作成では、GitHubの対象ブランチにある `cards/` 配下のカード画像だけを確認し、ワードを作成・照合します。それ以外の情報は一切参照しません。

カード画像のファイル名、カードID、妖怪名やその読み仮名は、ワードの発想・本文に使用しません。ワードはファイル名ではなく、画像に実際に描かれた情景だけを根拠に作成します。

各カードには、ゲーム内で使用する公式ワードを10個以上登録します。

### 作成ルール

公式ワードは、カードの情景を見たときの反応として作成します。単なる物の名前や情景説明だけで終わらせず、次のような形式・発想を同じカード内で混在させます。

- 情景への一言ツッコミ、ノリツッコミ、例えツッコミ
- 登場人物が言いそうなセリフや会話の一部
- 勘違い・失敗・別の出来事に置き換えた解釈
- 商品名・企画名・競技名・ニュース見出しのような表現
- ことわざ・慣用句・有名作品などをもじった表現
- 駄洒落、造語、意外な組み合わせ
- イラストから連想を広げた別の物語や状況
- 描かれた情景への疑問やツッコミ

10個すべてを同じ文型にせず、笑いの生まれ方と発想の方向を分散させます。特に「○○した結果」「○○の末路」「○○が○○している」「○○すぎる」「○○を間違えた」といった型だけを繰り返しません。

三点リーダー（`…`・`……`）で間や含みを作る表現、および感嘆符・句読点の後などに入れる不自然な全角スペースは使用しません。日常の会話として自然な句読点・改行・語順で表現します。

### イラストとの整合性

公式ワードは、イラストに明らかに描かれている内容と矛盾しないようにします。

ワードを作成するときは、次のような要素をイラスト上で確認します。

- 物体の種類
- 人物や動物の種類
- 物体の状態
- 開いているか、閉じているか
- 濡れているか、乾いているか
- 色や形
- 数
- 大きさ
- 位置関係
- 持っている物、身につけている物
- 表情や動作

イラストに描かれていない部分を想像した内容や、見えない事情への妄想、疑問形、これから起こることへの予想は、イラストに明らかに反しない限り使用できます。

一方で、イラストに描かれている物体・人物・動物・状態・位置関係などを、実際とは別のものとして断定する表現は避けます。

例えば、イラストにカバンが描かれている場合、それを封筒や別の道具として断定する表現は使用しません。

### 分かりやすさと自然さ

子どもでも意味を理解しやすく、親がその場で作ったワードとして自然に見える表現にします。少し難しい言葉や固有名詞も、ワード全体の意味が伝わり、カードのボケへの反応として成立していれば使用できます。

次のようなワードは避けます。

- 意味を理解するために長い説明が必要なもの
- 単独では意味が伝わりにくい単語だけのもの
- 親がその場で作ったワードとして不自然なもの
- カードの情景との関係が薄いもの
- イラストに明らかに反するもの
- 他の公式ワードと意味や構造がほぼ同じもの

発想の奇抜さだけでなく、ゲーム中に見たときの分かりやすさと、親ワードに紛れ込める自然さを重視します。

### 登録前の確認

公式ワードを登録する前に、カード画像とワードを一つずつ照合します。

- 公式ワードが10個以上あること
- ツッコミ、セリフ、例え、見出し、別解釈などの形式が混在していること
- 同じ文型や発想に偏っていないこと
- 見たままの説明だけで終わっていないこと
- 子どもでも意味を理解しやすいこと
- 親がその場で作ったワードとして自然に見えること
- イラストに明らかに反する内容がないこと
- 物体・人物・動物の種類を取り違えていないこと
- 状態や位置関係を、イラストと逆に断定していないこと
- 他のワードと意味や構造が重複していないこと

この確認では、イラストに描かれていない部分を想像していることだけを理由にNGとはしません。

NGとするのは、イラストに明らかに描かれている内容と異なる場合です。

例えば、次のような表現はNGです。

- 閉じている物を「開いている」と断定する
- 乾いている物を「濡れている」と断定する
- カバンを「封筒」と断定する
- 描かれている人物や動物を、別の種類として断定する
- 実際とは異なる位置関係を断定する

一方で、次のような表現は、イラストと矛盾しなければ使用できます。

- 描かれていない部分への想像
- 見えない事情への妄想
- これから起こることへの予想
- イラストに対する疑問
- 情景へのツッコミ
- 実際には確認できない裏側や後日談

例：

- イラスト：リンゴに鴨が刺さっている
- 公式ワード：`リンガモ`、`カモネギのリンゴバージョン`、`ウィリアム・テルが間違えたんか`、`ピコ太郎`

## カードデータ

カードセットごとに `cards/<カードセットID>/cards.json` で管理します。画面に表示するカードセットと初期選択は、ルートの `card-sets.json` で管理します。

現在の構成は以下です。

```text
cards/
├── test/
│   ├── cards.json
│   └── カード画像
└── vol1/
    ├── cards.json
    └── カード画像
```

- `test`：画面上では「お試し版」と表示するカードセットです。
- `vol1`：画面上では「ノーマルVOL.1」と表示するカードセットです。
- `yokai1`：画面上では「妖怪VOL.1」と表示するカードセットです。
- 各 `cards.json` は、カードセット名・カード一覧・ワードセット一覧を保持します。
- 人数選択画面では、カードセットをリストから選び、選択したカードセットに対応するワードセットを別のリストから選びます。
- カードセットの初期選択は `VOL.1` です。
- カードセットと、カードセットごとのワードセット選択は、次回起動時にも復元します。

```json
{
  "defaultCardSet": "vol1",
  "cardSetIds": ["test", "vol1"]
}
```

- 新しいカードセットを追加する場合は、`cards/<カードセットID>/cards.json` を作成し、`card-sets.json` の `cardSetIds` にIDを追加します。

```json
{
  "id": "vol1",
  "name": "VOL.1",
  "cards": [
    {
      "id": 1,
      "image": "カード画像ファイル名"
    }
  ],
  "wordSets": [
    {
      "id": "standard-1",
      "name": "標準セット",
      "cards": [
        {
          "cardId": 1,
          "officialWords": [
            "公式ワード1",
            "公式ワード2",
            "公式ワード3"
          ]
        }
      ]
    }
  ]
}
```

- `cards` にはカードIDと画像ファイル名を登録します。
- `wordSets` には、同じカードセットで使用するワードセットを登録します。
- `wordSets[].cards[].cardId` で画像カードと公式ワードを対応づけます。
- 公式ワードは各カードにつき10個以上を登録し、各ラウンドで重複なく3個を選びます。
- 同じカードは、同一ゲーム内で重複して使用しません。
- カード画像と `cards.json` は、同じカードセットのフォルダで管理します。
- 画像ファイル名と `cards.json` の `image` 指定を一致させます。
- カード画像は正常なPNG形式で登録します。
- 新しいワードセットを追加すると、同じカード画像で別の公式ワード群を使用できます。
- ワードセットを追加する場合は、対象カードセットの `cards.json` に `wordSets` を追加します。選択画面は登録済みの `wordSets` から選択肢を自動生成するため、通常はHTMLやJavaScriptの変更は不要です。

## 妖怪物語データの管理

### データの役割

- Google Drive上の `yokai` スプレッドシート：妖怪情報の正本
- `data/yokai.json`：ゲームで直接参照する妖怪情報データ
- `cards/yokai*/cards.json`：カード画像・公式ワードなどのカードゲーム用データ

妖怪情報は、Google Drive上の `yokai` スプレッドシートの `LIST` シートから取得します。使用する列はA列（妖怪番号）、B列（妖怪名）、D列（出現）、E列（特質）です。GitHubには、A・B・D・E列が揃った行だけを `data/yokai.json` として保持します。未完成行は含めません。

ゲーム実行時には、`data/yokai.json` を必要に応じて一度だけ読み込み、カード画像名に含まれる妖怪固有番号で照合します。物語本文はFirebaseへ保存しません。

### ファイル名と妖怪固有番号の照合

妖怪カード画像のファイル名は `XXX_妖怪番号_妖怪名.webp` とします。

- 第1要素 `XXX` はカードセットVOL内の連番です。
- 第2要素は全妖怪で共通の固有番号です。
- 固有番号の桁数は固定しません。 `005`、`999`、`1000`、`1234` を同じ規則で数値として扱います。
- Google Drive上の `yokai` スプレッドシートの `LIST` シートA列、および `data/yokai.json` の `number` との照合には、第2要素だけを使用します。

`LIST` シートから `data/yokai.json` へ反映する対応は、A列→`number`、B列→`name`、D列→`appearance`、E列→`traits` です。本文は要約・言い換え・整形による内容変更をせずに保存します。

`number` はJSONでは数値として保存します。ゲーム画面では最低4桁のゼロ埋めで `No.0005`、`No.0087`、`No.0999`、`No.1000` のように表示し、1000以上の番号を切り詰めません。

### 現在の運用フロー

Google Drive `yokai`
↓
`data/yokai.json`
↓
ゲームから直接参照

Googleスプレッドシートから `data/yokai.json` を更新する作業だけを、妖怪物語データの更新作業とします。AIが `cards.json` へ妖怪物語を手作業で転記したり、物語同期スクリプトを実行したりする運用は行いません。

対象ブランチは依頼で指定されたブランチおよび本READMEのブランチ運用ルールに従います。

## カード追加・公開手順

新しいカードを追加する際は、以下の手順で進めます。

1. 新規カードのイラストを確認し、カードの情景に対する公式ワードを10個以上作成します。
2. 作成した公式ワードをカード画像と一つずつ照合し、イラストに明らかに反する内容や、物体・人物・動物・状態の取り違えがないことを確認します。
3. 描かれていない部分への想像や疑問、ツッコミは、イラストと明らかに矛盾しない限り使用できます。
4. 既存カードと題材・発想・公式ワードの切り口が偏らないことを確認します。
5. 追加するカードには、既存の続き番号を付けます。
6. カード画像の作成時にカード番号の指定がある場合は、ライブラリ保存時点からGitHubへアップロードする最終ファイル名を付けます。例：11枚目の「雲を刈る床屋」は `card-011-cloud-barber.png`。
7. カード画像は、横1024×縦1536ピクセルの正常なPNGとして作成します。
8. カード画像は、`cards.json` の `image` と完全に同じファイル名でライブラリに保存します。
9. `cards.json` に、カードID・画像ファイル名・公式ワードを追加します。
10. カード画像は、GitHubの画面から手動で `cards/<バージョン名>/` へアップロードします。既存カードの差し替えでは、同名の画像ファイルを置き換えます。
11. アップロード後、GitHub上で以下を確認します。
   - 画像ファイル名と `cards.json` の `image` 指定が一致していること
   - 全画像が正常なPNGとして開けること
   - 画像サイズが横1024×縦1536ピクセルであること
   - `officialWords` が各カード10個以上あること
   - GitHub Pages上でもカード画像を読み込めること
12. 上記をすべて確認できるまで、追加作業を完了扱いにしません。

カード画像は、GitHubへ登録する際に画像変換・圧縮を行わず、作成済みのPNGデータをそのまま使用します。

## 現在の実装

1台のスマートフォンを順番に操作するローカル版と、各自の端末から参加する通信対戦版を実装しています。

実装済みの主な機能：

- プレイヤー人数の登録（2〜6人）、選択人数の保存と次回表示時の復元
- カードセット選択の保存と次回表示時の復元
- カードセットごとのワードセット選択の保存と次回表示時の復元
- プレイヤー名の入力、対戦人数に依存しない保存・復元
- 空欄・重複名のチェック
- 親順の初回ランダム決定と以後の固定順交代
- 各操作前の本人確認
- カードのランダム表示と重複使用防止
- 公式ワード3個のランダム選択
- 親ワードの入力

### ひそめごと開帳の演出

「ひそめごと開帳」を押すまでは、4つのワードを同じ見た目で表示します。押した後は、停止前の動きが10種類からランダムに選ばれます。1〜3は親ワードに停止するまで約4.95秒、4〜6は約5.7秒、7〜9は約6.5秒、10は約10秒です。各演出は、素直に回る・行き過ぎて戻る・左右に迷う・止まりかける・再び速くなるといったテンポと芝居の型として維持します。一方で、開始位置・回る向き・切り返す地点・終盤の経由候補は毎回ランダムに組み替えます。そのため、同じ型を覚えても最後の動きから正解位置を逆算できません。停止後は、親ワードの枠を約1.05秒、太い金枠と発光で点滅させます。演出が完了するまで「得点を確認」は押せません。

### 最終勝利画面の演出

勝利画面では、今回の宴で使用した全ラウンドのお題カードを、左右から交互に中央へ滑り込ませて重ねる。カード束はその後に上部へ小さく退き、「今宵の勝者」、勝利イラスト、勝者名、得点一覧の順で表示する。勝者が複数いる場合も、カードは特定の勝者の戦果として扱わず、「今宵を彩った札」として全員共通の演出にする。端末が動きを減らす設定の場合は、カード束と結果を即時表示する。

## DEV Firebaseデータの清掃

`Cleanup DEV Firebase` ワークフローは、DEV Realtime Databaseの `rooms/{roomId}/createdAt` が実行時点から7日より前の部屋と、その部屋IDにひもづくデータを削除します。`firebase-test` は `connectedAt` が7日より前のデータを削除します。作成時刻を判定できないデータは削除しません。

実行には、DEV FirebaseプロジェクトのサービスアカウントJSONをRepository secret `FIREBASE_SERVICE_ACCOUNT_DEV` に登録する必要があります。現在は `develop` 配置のため `workflow_dispatch` による手動実行だけです。`main` へ反映するときに、GitHubのデフォルトブランチ上で1日1回実行する `schedule` を追加します。

## 開発方針

- ブラウザ上で遊べるゲームとして制作します。
- まずは1台のスマートフォンで遊べるローカルゲームを完成させます。
- カード画像と公式ワードは事前に作成して登録します。
- ゲーム中にAIでイラストや公式ワードを生成する機能は実装しません。
- ソースコードはGitHubで管理します。
- 修正時は既存機能を壊さないよう確認してから変更します。
- 実装・更新の依頼を受けた変更は、GitHub接続経由で `main` または依頼で指定された対象ブランチへ反映します。反映前の個別承認文や通常の `git push` は不要です。
- GitHub接続経由で対象ブランチへ反映できた時点で、その変更は完了扱いとします。GitHub Pagesの公開反映待ちや公開URLでの確認は完了条件に含めません。
- 複数ファイルの変更は、GitHub接続経由でも1コミットにまとめて反映します。
- 反映できない場合のみ、原因と未反映の内容を報告します。
- カード画像はテキストとして扱わず、正常なバイナリPNGとして登録します。
- 画像を追加・差し替える際は、公開前にPNG/JPEGとして読み込める有効な画像ファイルであることを確認します。拡張子だけが画像形式に見える壊れたデータは登録しません。
- 画像URLには、キャッシュ更新のための`?v=`などのバージョン表記を付けません。画像の差し替え後は、GitHub Pagesの公開反映を確認します。
- GitHubへ反映後は、公開URLでHTML、JavaScript、`cards.json`、カード画像の読み込みを確認します。
- 画像、CSS、JavaScriptを含むすべての公開URLに、キャッシュ更新のための`?v=`などのバージョン表記を付けません。GitHub Pagesの公開反映を確認してから、通常の再読み込みで確認します。
- キャッシュ番号の更新を目的としたGitHub Actionsや、自動コミット・自動pushの仕組みは使用しません。
- 将来的な複数端末によるオンライン対戦への拡張を考慮します。

## 通信対戦仕様

通信対戦の確定仕様・未確定事項・実装順序は、[通信対戦仕様書](docs/multiplayer-spec.md)を正本として管理します。

- 通信対戦を実装・変更する前に、必ず仕様書を確認します。
- 通信対戦の仕様変更・実装変更は、画面文言・UI配置・操作条件・通信状態を含め、コードと同じコミットで仕様書も更新します。完了報告は仕様書の更新確認後に行います。

通信対戦では、全プレイヤーが1回ずつ親になる一巡を「第○席」、その中の個別の親番を「○番手」とします。各席の開始時は `parentUid` を設定せず、全員が自分専用のカードと親ワードを同時に仕込みます。全員が `ひそめる` を完了した後、主催者端末が一番手の開始を原子的に確定し、その時点で初めて `parentUid` を設定します。

- 仕込み中のカード・公式ワード・親ワード・正解位置は `roomPreparations` の本人専用領域に保存し、他の参加者には公開しません。
- 仕込みの進捗だけを `roomPreparationProgress` で共有し、名前パネルに `札選び中`、`ひそめ中`、`完了` を表示します。
- カードは `roomCardReservations` で原子的に予約し、同じカードの同時取得と、引き直し前カードの再利用を防ぎます。
- 一番手以降は仕込み済みデータを使い、得点後に同じ席の未実施者がいれば `次の番手へ`、最後の番手なら `次の席へ` と表示します。
- 次の席では再び `parentUid` なしの一斉仕込みへ入り、全員完了まで一番手を開始しません。
- 仕込み秘密データと進捗はFirebaseに保存するため、札選び前・ひそめ中・完了待機の各状態から再読込復帰できます。入力確定前の親ワード文字列だけは復元しません。
- ゲーム内の「親・子」と通信上の「主催者・参加者」を混同しません。
- 未確定事項を推測で実装せず、仕様書上で確定事項と分離します。
